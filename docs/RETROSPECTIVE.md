## 2. 时间去向（真实数字）

```
Pi 5 轮串行         67.6 min   47%   ← 每轮都要重读 README/架构/施工单并重建上下文
Hermes 调查+验收    约 40 min   28%
CC 架构+Review      14.5 min   10%
等待/切换/收尾      约 22 min   15%
总计               约 144 min  100%
```

放大因素（按影响排序）：

1. **轮次数量**：我把实现拆成 4 轮（Route Review 时已从 CC 的 7 轮合并过），缺陷又加 1 轮 = 5 轮。每轮的固定开销（读文档 + 重建上下文 + 跑全量 pytest）约 2–3 min，5 轮就是 10–15 min 纯开销。
2. **单轮模型速度**：Pi 平均 13.5 min/轮；CC 的 API 侧 34 轮只用了 5.2 min（≈9 s/轮，Review 多为 grep/read），架构 14 轮 9.3 min（≈40 s/轮）。**MiniMax-M3 单轮确实明显更慢**，但轮次才是主因。
3. **串行依赖**：P2→P3→P4 有真实依赖，无法并行；这是设计粒度问题，可以通过"合并成 2 轮"缓解，而不是靠并行。

## 3. 发现的问题（按性质分类，含责任归属）

### 3.1 流程问题（我自己造成，最大的一条）

**问题**：为了实现"每轮可独立验收"，把粒度切得过细，导致 5 轮串行。
**代价**：约 10–15 min 纯上下文开销（约 10% 总时长）。
**改进**：已定型的中小项目应合并为 **2 轮**（基础层+reader 一轮；CLI/UI/集成一轮）。已写入 `multi-agent-project-delegation` 技能第 10 条。

### 3.2 设计问题（CC，验收阶段才暴露）

**问题**：架构文档把 z.ai 的 `percentage` / `nextResetTime` 当作恒存在字段，未声明"该字段可能缺失"这一假设 → 实现据此写成硬校验 → 窗口刚重置时整个 provider 掉线（D-006）。
**逃逸路径**：设计阶段（CC 未查该状态）→ 实现阶段（Pi 按文档实现，无错）→ 验收阶段（Hermes 交叉核对时暴露）。
**改进**：架构文档里每个上游字段都应标注**"必然存在 / 可能缺失 / 语义可能反转"**三态。这条作为下一次施工单模板的固定字段。
**注意**：这不是 Pi 的错，也不该判 CC 失败——CC 无法穷举未知状态；但可以要求它显式标注假设，让验收有靶子。

### 3.3 工具链问题（桥接与权限）

1. **CC 首次运行被权限全拦**（`--allowedTools` 不够，需 `--permission-mode bypassPermissions`），损失约 3 min 且产生一次"拒绝交付"。已写入 `claude-code` 技能。
2. **桥接状态机与真实产物不一致**：P1 报 ERROR（2 个工具错误，但产物完整）、P3 报 TIMEOUT（900s 截断，产物完整）、P5 报 ERROR（`Connection error.`，产物完整）。**3/5 轮的桥接状态都不可作为判定依据**。已写入技能：先读产物再判失败。改进：桥接应把"最后一个 assistant 消息是否含完成语义 + 产物是否存在"纳入状态判定，而不只看流里的错误事件。

### 3.4 我自己的遗漏

**问题**：我在 15:11 曾验收过 z.ai（当时窗口有字段，一切正常），但没有追问"这个字段在什么状态下会消失"。一个上游接口的**状态相关契约**只验一次是不够的。
**改进**：对每个外部数据源，验收至少要覆盖"正常态 + 边界态（归零/刚重置/空数组/超限）"两种，不能只测当下这一次真实响应。这条已构成 D-006 的直接教训。

### 3.5 分工问题

**Codex 零参与**：符合"谁最合适"原则（v0.1 确无本机集成需求），但存在隐性风险——如果连续几个项目都不用 Codex，说明它在我们栈里的定位需要重新论证（是"备用工程师"还是"根本没有独立价值"）。建议在 v0.2 或下一个需要 Windows 集成的项目里刻意给它一个任务验证定位。

### 3.6 效率与成本

- CC 两轮合计 **$2.78**（GLM 走 CC Switch 代理记账）；Pi 走 MiniMax 订阅，单轮 cost 记 0；我方（DeepSeek）用量未计。
- 性价比判断：**$2.78 换一份 28KB 可用架构 + 一份有真证据的独立 Review，值**。真正的浪费不是钱，是 5 轮串行的时间。

## 4. 值得保留的做法（不要改掉）

1. **命脉先于代码**：先手工打通 4 家数据源再派工。这一次直接决定了 MiniMax 必须自写 Reader、DeepSeek 只能做 balance —— 若反过来，返工量远超省下的 30 分钟。
2. **不接受 Agent 自述**：唯一阻塞缺陷由我独立验收 + 原始源交叉核对抓出，三个 Agent 的自检全部报 PASS。
3. **Route Review 不放水**：收回终验权、砍多余状态机、加解释器版本约束（本机三个 Python 的真实风险）、fixtures 脱敏、凭据 fallback —— 全部在 3 分钟内改完，避免了后续返工。
4. **真相边界显式化**：`updated_at=null` + UI `~` 前缀（D-007）这种"不许污染源真相"的规则，写进决策文档后就不会被后续 Agent 悄悄改掉。
